## 2.1 Continuous Integration and Continuous Deployment

Continuous integration, continuous delivery and continuous deployment are software development practices that allow development teams to deliver software frequently and reliably. These practices use automation for activities such as integrating code, testing software and supporting the release process (Shahin et al. 2017). However, continuous practices also involve practical challenges. For example, builds and tests may take too long, automated testing requires effective support, build and test results need to be clearly visible, and deployment reliability can be a concern. Because of these issues, the performance and reliability of CI/CD pipelines are important areas for systematic analysis (Shahin et al. 2017).

Continuous Integration has been widely researched and can bring several benefits to software development. It can improve development activities, software processes and quality assurance, but it can also create technical and process-related challenges (Soares et al. 2022). The effects of CI are not limited to a single area, as CI can influence build patterns, defects, integration practices and other parts of the development process (Soares et al. 2022).

Continuous Integration means that developers frequently merge new or changed code into the main codebase, and testing is important both before and after this integration. Fast feedback is one of the main benefits of CI, but slow or inefficient testing can delay that feedback (Elbaum et al. 2014). Elbaum et al. (2014) also explain that regression-test selection and test-case prioritization can make CI testing more cost-effective, and the authors present algorithms to support this process.

Continuous Integration is a practice where developers frequently integrate their changes into a shared main codebase. Each change is checked by an automated build and tests. Every push to the main codebase should start a CI build, and this build should be fast so that developers get feedback quickly (Fowler 2024). The team should also be able to see the build status and test results easily, so everyone knows the current state of the integration (Fowler 2024).

Continuous Delivery focuses on making software releases reliable and low risk by automating build, testing and deployment work. A deployment pipeline helps to transfer software changes from integration to release in a controlled and repeatable way, and fast feedback is important so that problems can be found quickly (Humble & Farley 2010). Humble and Farley (2010) also show that pipeline performance should not be evaluated only by speed, because software quality and release reliability must also be maintained. They also support frequent and small delivery steps as a way to improve the software delivery process.

## 2.2 GitHub Actions and CI/CD Workflow Execution

A GitHub Actions workflow is an automated process that is defined in a YAML file and stored in the `.github/workflows` directory of a repository. A workflow can start because of repository events, manually, or according to a schedule, and it includes one or more jobs (GitHub s.a.). Each job runs on a runner and contains one or more steps, and each step can run a script or a reusable action (GitHub s.a.). This structure is useful for the thesis because the iSign CI/CD data is organised in the same way: workflow, workflow run, job, and step.

The GitHub REST API can be used to collect GitHub Actions workflow runs, and these runs can be filtered by branch, event, status, and creation time (GitHub s.a.). A workflow run is one execution of a workflow, and the API can also return the jobs that belong to that run. Each job has a set of steps that run on the same runner, so workflow and job data can be collected by a program instead of manually (GitHub s.a.). This supports the thesis data-collection process because historical iSign workflow-run and job-level data can be retrieved using a Python script.

## 2.3 CI/CD Pipeline Performance

Continuous Integration helps teams build software at frequent intervals, but long build times can delay feedback and prevent developers from doing other important work. Ghaleb et al. (2019) analysed 104,442 CI builds from 67 GitHub projects and showed that many factors can be linked to long build times, not only common ones such as project size or test density. They also found that repeatedly running failed commands is strongly linked to longer builds, while caching items that do not change often and finishing builds as soon as all required jobs are completed may help to reduce build time. The authors suggest that developers should use proper CI build settings and that tool builders should help identify the parts of a project that can be cached (Ghaleb et al. 2019).

## 2.4 Statistical Baseline and Anomaly Detection

Anomaly detection is an important problem that has been studied in many different research areas. Its main aim is to find patterns that are different from normal behaviour. There are many different methods, and they can be grouped based on how they work (Chandola, Banerjee & Kumar 2009). Each method has different assumptions about what is normal and what is anomalous, so whether a method is suitable depends on the data and the area where it is used. The survey also shows that the computer resources required by the method are an important factor to consider when choosing an anomaly-detection method (Chandola, Banerjee & Kumar 2009).

An outlier is a data point that is very far away from the other points in a data set. Before unusual points can be identified, it is first necessary to understand what normal behaviour looks like. The interquartile range is used together with the lower and upper fences (Q1 - 1.5 × IQR and Q3 + 1.5 × IQR) to identify possible outliers. Points outside these fences can be considered possible outliers, but they should be checked carefully instead of being removed automatically, because they may contain useful information about the process or the data collection (NIST s.a.).

## 2.5 Isolation Forest

Isolation Forest is an anomaly-detection method that works differently from methods which first build a profile of normal data. Instead of profiling normal data, it tries to isolate anomalies directly by randomly splitting the data. Anomalies usually get isolated with shorter paths in the isolation trees (Liu, Ting & Zhou 2008). The method does not need labelled anomaly examples for training, and it is fast with relatively low memory use. The original study also showed that Isolation Forest performed competitively compared with several other methods, especially on large datasets and high-dimensional problems (Liu, Ting & Zhou 2008).

## 2.6 Measurement and Evaluation in Software Development

Evaluating unsupervised outlier-detection methods is difficult because not much is known about the strengths and weaknesses of different models. Also, the effects of parameter values are not always clear. A major problem is that benchmark datasets with reliable correct answers, or ground truth, are difficult to find, and even when labelled data is available, it may not be suitable for outlier detection (Campos et al. 2016). The paper also explains that commonly used evaluation methods can have their own biases, so it can be difficult to know whether a new method really performs better than existing ones. To study this problem, the authors carried out a large experimental study using nearest-neighbour-based methods across many datasets and suggested better ways to evaluate the results (Campos et al. 2016).

A designed experiment is a planned activity where one or more factors are changed on purpose so that their effect on one or more response variables can be observed. The aim of the experiment and the factors should be decided before any measurements are collected. When one main factor is studied, the results can be compared across different levels of that factor. It is also better to carry out more than one experimental run than to depend on only one measurement, and possible unexpected changes or gradual changes in the process should be taken into account (NIST s.a.). Finally, the raw data should be kept, important events should be recorded, and the results should be analysed and interpreted carefully after the experiment (NIST s.a.).
